# MeshSat OOB management frames, specification v1.1 (2026-09-01)

Status: APPROVED for implementation (MESHSAT-756, plan approved 2026-09-01). Spec first, code second. Test vectors in section 14 are generated by the reference implementation in `internal/oob` and pasted here when step 2 of the work order lands.

Changes from v1.0 (draft of the same day): nonce carries a control byte (sender role and direction) and each sender keeps one counter for requests and replies; every reply carries a result code, the request counter and chunk numbering; the peer id is derived from the key; the argument cap is 73 bytes with per-bearer reply budgets; NET-RESET is replaced by `RESET <target> <level>` over every interface and the host, three levels; corrections from the code audit (`aprs_0`, decode-first boundary classifier, SMS sender address, per-delivery destination and class, mesh addressing, directed APRS messages, tmpfiles.d, kit-local compose); both key provisioning paths; boot-time counter bump; reply encryption mirrors the request; frames received while the feature is disabled are dropped.

## 1. Problem and scope

On 2026-09-01 parallax sat healthy (battery 98 percent, AC on, bridge up, LTE registered) while its only management path, WiFi, was being deauthed by the access points every few seconds and finally dropped entirely. No path existed to tell the kit anything, although it had four other bearers alive. This is the gap MESHSAT-751 names as "a real out-of-band path before the 1 Nov field programme".

Goal: an operator or a peer kit can send a small, authenticated, optionally encrypted command to a kit over ANY bearer the kit has (SMS, APRS, Meshtastic LoRa, Iridium MT, Hub MQTT, later BLE and Reticulum links), the kit executes it from a fixed allowlist, records a signed audit entry, and answers on the bearer the command came in on.

Non-goals, permanently: shell access, arbitrary file writes, config import, key rotation over OOB, chat. Also not a new Reticulum interface: this is a message class that rides the existing interfaces. No polling and no heartbeats on paid bearers (standing rule: protocol overhead never goes to paid interfaces). No netplan writes in v1.

## 2. Bearer budgets (fixed physical facts)

| Bearer | Frame budget | Reply args budget | Latency | Cost per reply |
|---|---|---|---|---|
| APRS directed message | 67 chars of message text | 15 bytes | seconds, needs a station in range or an igate with TX | free |
| SMS (GSM-7) | 160 chars | 72 bytes | seconds to minutes | about EUR 0.10 (KPN prepaid) |
| Meshtastic text | about 200 bytes | 73 bytes | seconds | free |
| Iridium MT 9603 SBD | 120 chars on the plaintext path | 48 bytes | minutes | paid |
| Iridium MT 9704 IMT | large, pushed | 73 bytes | minutes | paid |
| Hub MQTT, TCP, BLE | large | 73 bytes | sub-second | free |

Encryption is an operator toggle per peer and per bearer on every bearer, APRS included (owner ruling 2026-09-01). Whether to turn it on for a given band under a given licence is the operator's decision and appears only as a one-line caveat in the documentation, never as a code path.

## 3. Frame format

One frame is one command or one reply. Fixed header, short body, 16-byte tag.

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | magic 0x4F ("O") |
| 1 | 1 | flags: bit0 ENC (body encrypted), bit1 REPLY, bit2 NOREPLY (do not answer), bits 4 to 7 version (1) |
| 2 | 2 | peer id, uint16 big-endian, derived from the key (section 4), never 0 |
| 4 | 4 | counter, uint32 big-endian, the sender's single monotonic counter (requests and replies share it) |
| 8 | 1 | cmd (section 6); a reply echoes the request cmd |
| 9 | n | args, at most 73 bytes, plaintext or AES-256-GCM ciphertext |
| 9+n | 16 | AES-256-GCM tag |

Minimum frame is 25 bytes, maximum 98. AEAD is AES-256-GCM under the per-peer key. Associated data is bytes 0 to 8 when ENC is set; when ENC is clear the args are appended to the associated data and the ciphertext is empty, so the same primitive produces a pure authentication tag. One code path, one flag.

Nonce (12 bytes) is deterministic and not transmitted: peer id (2) || ctl (1) || counter (4) || zero (5), where ctl = (sender role << 1) | direction, direction 0 for a request and 1 for a reply, sender role 0 for the peer that issued the key (or the lower dest hash on the ECDH path) and 1 for the other side. The receiver derives ctl from the REPLY flag and from its own role. A nonce is never reused because each sender persists its counter before transmitting, the two roles never collide, and the receiver's replay window rejects reuse. Restore from an older backup could rewind a counter, so the bridge bumps every peer's transmit counter by 65536 at each boot; the key is exhausted at 0xFFFFFFFF and the sender refuses with KEY_EXHAUSTED.

Text encoding: the whole frame in Crockford base32 (alphabet 0123456789ABCDEFGHJKMNPQRSTVWXYZ, no padding) behind the sentinel `MS:`. Decoding is case-insensitive and maps I and L to 1 and O to 0; U is invalid. A frame can be read over a voice channel and typed at the other end. A 25-byte frame is 40 characters, a 98-byte frame is 157, so `MS:` plus the largest frame is exactly one 160-character SMS.

Placement per bearer: APRS as a directed message to the kit's callsign (`:CALL-SSID:MS:...`); SMS as the message text; Meshtastic as a text message to the kit node (a phone with the Meshtastic app can send it); Iridium MT as the payload text; Hub MQTT as the existing command envelope.

## 4. Keys, peers, roles

Per peer one 32-byte AES-256 key in the keystore under the channel type `mgmt` (bundle enum 0x08; older bundle readers skip unknown types, the documented compatibility path in `internal/keystore/bundle.go`). The address is the peer alias, so the key for talking to peer P is `mgmt:P` on both sides.

Peer id = the first two bytes of SHA-256 over the label `meshsat-oob-peer-id` and the key, big-endian; the value 0 maps to 1. Both sides derive the same id from the same key with nothing extra on the wire or in the bundle.

Provisioning, both paths in v1:

- Bundle path: the issuing kit generates a random key, stores it under `mgmt:<peer alias>` with role issuer, and emits it inside the existing signed key bundle QR (`meshsat://key/`) as an entry of type `mgmt` whose address is the issuer's own alias. The importing side (a kit or the Android app) stores `mgmt:<issuer alias>` through the existing key import and registers the peer with role importer, `readonly` until an operator promotes it. Same exposure as today's SMS and APRS keys.
- ECDH path, for peers that are kits: the peer's X25519 public key comes from its Reticulum announce (kept per destination in the routing table, looked up through `trusted_peers.routing_identity`). Key = HKDF-SHA256(ikm = X25519(my private, peer public), salt = `meshsat-oob-v1`, info = `meshsat-oob-mgmt-key` || lo || hi) where lo and hi are the two 16-byte destination hashes sorted; the lower hash takes role issuer. No key material leaves either kit.

Peer record: peer id, alias, optional signer id (when the peer is a kit), key reference, key source, local role, role (`readonly` or `control`), enabled, per-bearer addresses (interface id to bearer address: phone number, callsign-SSID, mesh node id), per-bearer encryption policy for requests this kit originates (absent means encrypt), transmit counter, receive window, timestamps.

Roles: `readonly` may PING, STATUS-NET and LOG; `control` may do everything. Revocation revokes the key and disables the row; a revoked peer's frames are dropped before anything beyond the header is parsed.

The bearer-level sender address is never used for authentication. It is recorded and used as the reply destination. `cellular_0.allowed_senders`, when configured, drops SMS before the classifier sees them, so an operator number must be listed there as well; that is defence in depth and stays.

## 5. Replay protection

RFC 6479 style sliding window per peer, 64 bits wide, persisted on every accepted frame. Accept when the counter is greater than the highest seen, or within 64 below it with its bit clear. Counter 0 is never valid. No timestamp in the frame: the kit whose clock is wrong is the one you need to reach. A reply carries the kit's clock so the operator can see skew.

Unauthenticated, replayed, unknown-peer, disabled-peer and disabled-service frames get silence: no reply of any kind, so there is no oracle and no way to run up the kit's SMS bill. They are counted in metrics and the first rejection per peer per hour is audited. A frame received while the feature is disabled is dropped, never treated as chat.

## 6. Commands (v1)

| Code | Name | Request args | Role | Action |
|---|---|---|---|---|
| 0x01 | PING | none | readonly | none |
| 0x02 | REBOOT | delay seconds uint16, default 10, max 3600 | control | ACK first, then the host agent schedules `systemctl reboot` after the delay |
| 0x03 | RESTART | none | control | ACK first, then the bridge's own restart path (SIGTERM, Docker restarts the container) |
| 0x04 | RESET | target byte, level byte (1, 2, 3) | control | section 7 |
| 0x05 | BEARER | target byte, state byte (0 off, 1 on) | control | gateway instance stop or start plus the interface enabled flag |
| 0x06 | LOG | unit byte, lines byte (1 to 20) | readonly | host agent journal tail, chunked |
| 0x07 | STATUS-NET | none | readonly | network summary from the host agent, in-container fallback |

Every reply echoes the request cmd and carries `[rc:1][request counter low 16 bits:2][seq:1][total:1][body]`. Result codes: 0 OK, 1 DENIED, 2 BADARGS, 3 UNAVAILABLE, 4 REFUSED (self-severance guard), 5 AGENT_ERR, 6 UNKNOWN_CMD, 7 BUSY, 8 KEY_EXHAUSTED. Reply encryption mirrors the request: a frame typed by hand in clear gets a readable answer.

PING body, ASCII, most important first so the APRS budget keeps the head: `u17h b98A q0 wU-61 t1432Z sB7` (uptime, battery percent with A for AC or B for battery, queued deliveries, wlan up or down with RSSI when known, UTC HHMM, bearers-up bitmap in hex over the target table order).

Two executor rules. Every command is idempotent, so a duplicate delivered by a retry does no harm and the reply carries the request counter so the operator can match it. A command may never sever the bearer it arrived on without protection: hard RESET, REBOOT and RESTART require another bearer to be up unless the origin is the Hub, and BEARER off on the arriving bearer arms a 10-minute revert. The reply is queued before any disruptive action executes.

## 7. RESET targets and levels

Levels: 1 soft (in-process reconnect of the transport or gateway), 2 device (a reset the device itself understands), 3 hard (USB re-enumeration, power pin cycle, host reboot). Unsupported combinations answer UNAVAILABLE and do nothing.

| Code | Target | Level 1 | Level 2 | Level 3 |
|---|---|---|---|---|
| 0x01 | wifi | wpa_supplicant reassociate (agent) | restart wpa_supplicant and networkd (agent) | none in v1 |
| 0x02 | usb_wifi | restart the P2P link unit when enabled (agent) | same | USB rebind (agent) |
| 0x03 | cellular | transport reconnect | AT+CFUN=1,1 | USB reset |
| 0x04 | mesh | transport reconnect | Meshtastic admin reboot | USB reset |
| 0x05 | iridium (9603) | transport reconnect | none | OnOff power cycle (needs the OnOff pin) |
| 0x06 | imt (9704) | transport reconnect | I_EN cycle | USB reset |
| 0x07 | zigbee | coordinator reinit | ZNP SYS_RESET_REQ | USB reset |
| 0x08 | ble | interface stop and start | adapter cycle | bluetooth service restart (agent) |
| 0x09 | aprs | gateway stop and start (respawns Direwolf, resets the AIOC) | same | AIOC USB rebind (agent) |
| 0x0A | gps | reader reopen | none | USB reset |
| 0x0B | rtl_sdr | spectrum recalibrate | none | USB reset by sysfs id |
| 0x7E | bridge | RESTART | | |
| 0x7F | host | | | REBOOT |

After any level 3 action the bridge triggers an immediate USB scan so the existing hot-swap recovery (device supervisor, gateway manager retry ladder) restarts the gateway within seconds. `/sys` is read-only inside the container, so in-process hard resets use the USB reset ioctl on `/dev/bus/usb`; sysfs unbind and rebind live in the host agent only. Reset targets whose follow-up flag is set send one unsolicited STATUS-NET style reply 30 seconds later on the same bearer.

## 8. Execution architecture, mapped to the code

New package `internal/oob/`: frame codec and AEAD, replay window, key derivation, command and target tables, executor, status builders, host agent client, service, metrics. The package never imports the engine, API, gateway or Hub packages; everything it needs arrives as closures or small interfaces.

Inbound hook points, one check each, before the rules engine:

- `Processor.StartGatewayReceiver` in `internal/engine/processor.go`: covers every gateway (SMS, APRS, Iridium, MQTT, webhook, TAK). The interface's ingress transforms are applied to a copy first (SMS and APRS may carry channel encryption), then the classifier looks for the `MS:` token at the start of the text or after whitespace, `]`, `>` or `:` (APRS plaintext arrives as `[APRS:CALL→ADDR] MS:...`; `SMS:` never matches), takes the run of base32 characters, and only if the header parses does it consume the text. Everything else falls through untouched.
- `Processor.handleMessage` for Meshtastic text, after deduplication and before persistence, sender `!nodeid`.

Frames never enter `messages`, never reach `DispatchAccess`, are never forwarded to another bearer and never trigger a rule. They are logged in `oob_log` and in the signed audit chain via `SigningService.AuditEvent("oob_command", ...)` with JSON detail.

Interface ids: the APRS gateway is `aprs_0` (`ax25_0` is the Reticulum routing interface, a different object).

Hub path: the executor is shared with `hubreporter.CommandHandler`. Hub commands `mgmt_ping`, `mgmt_status`, `mgmt_reset`, `mgmt_bearer`, `mgmt_log` and `reboot` (with `confirm: true`) call the same executor with peer id 0 and bearer `hub`, so Hub-originated and OOB-originated commands have one implementation and one audit path.

Replies go through the delivery ledger via `Dispatcher.SendToRecipient` with a raw recipient (interface id plus bearer address). Migration v54 adds `destination` and `delivery_class` to `message_deliveries`; the delivery worker passes the destination to the gateway (SMS destination, directed APRS message via `EncodeAPRSMessage`, mesh `To`) and, for class `oob`, skips the egress-rule gate and the interface egress transforms (the frame carries its own AEAD; interface-level encryption would hide the sentinel from a peer without the interface key). OOB deliveries are sent verbatim (no SMS prefix, no attribution). Inbound SMS now records the sender number as the message's from-address, which is also the reply destination.

Host agent: `deploy/oob/meshsat-oob-agent` (Python, stdlib only) behind `meshsat-oob-agent.socket` on `/run/meshsat-oob/agent.sock`, directory created by tmpfiles.d (never `RuntimeDirectory`, which would leave the container's bind mount on a dead inode after an agent restart), the DIRECTORY bind-mounted into the container. One JSON line per request, one per reply. Allowlist: ping, reboot, journal_tail, net_status, wifi_reassociate, wifi_restart, p2p_restart, usb_rebind, service_restart; every argument is a table lookup or a clamp, nothing is interpolated into a shell string, every call is logged. The container already runs privileged in standalone mode, so the allowlist is defence in depth and a declarative record of what the kit will do. Installed by `scripts/install-oob-agent.sh`, which also adds the mount to the kit-local `/srv/meshsat/docker-compose.yml` (backup, validation, no automatic bridge restart). Without the agent the bridge answers PING and STATUS-NET from in-container sources and UNAVAILABLE for host actions.

Bridge API, chi routes with full Swagger annotations: `GET/PUT /api/oob/config`, `GET/POST /api/oob/peers`, `PUT/DELETE /api/oob/peers/{id}`, `POST /api/oob/peers/{id}/bundle`, `GET /api/oob/peers/{id}/bundle/qr`, `POST /api/oob/send`, `GET /api/oob/log`, `GET /api/oob/targets`, `GET /api/oob/agent`. SSE events `oob_command` and `oob_reply`. Prometheus: `meshsat_oob_frames_total{result}` and `meshsat_oob_commands_total{cmd,result}`.

UI: Settings > Remote Mgmt (engineer shell only): configuration, peers with role and enabled toggles and per-bearer addresses and per-bearer encryption toggles (default on for every bearer, APRS included), a send panel, and the log. Verified with Playwright before it is called done.

Config, first-boot defaults only, everything UI-managed afterwards: `MESHSAT_OOB_ENABLED` (false), `MESHSAT_OOB_REPLY_BUDGET` (12 per peer per hour), `MESHSAT_OOB_HOST_SOCKET` (`/run/meshsat-oob/agent.sock`).

## 11. Test plan

Vectors: a fixed key, fixed frames, expected base32 strings for both encodings; tag failure on a flipped bit; replay window edges. Unit: role checks, refusal of a self-severing command, reply budget, the classifier never reaching the rules engine (asserted), false-positive guards (`SMS: hello`, `MS: test`). Integration: mock gateway to frame to executor to a delivery row with the destination set; host agent behind a mock socket. Field: SMS round trip tesseract to parallax with latency measured; APRS kit-to-kit in the same room in clear and encrypted; RESET levels on mesh and cellular with automatic recovery; BEARER revert; REBOOT with a delay while SSH is watched; replay and garbage frames answered with silence; regression of normal SMS, APRS and mesh traffic. Every reset step on a kit is done with Ethernet plugged in, per the standing rule on sole management paths.

## 12. Threat model

| Threat | Mitigation |
|---|---|
| Spoofed sender (trivial on SMS and APRS) | the tag, never the address |
| Replay of a captured frame | persisted sliding window per peer |
| Garbage flood, SMS bill amplification | silent drop, cheap header check first, per-peer reply budget, metrics |
| Stolen operator device | per-peer key and revocation, roles, counters make the old device's frames stale |
| Operator locks themselves out | self-severance guard and 10-minute revert timers |
| Key material in a QR (bundle path) | same exposure as today's SMS and APRS keys; the ECDH path has none |
| Audit flood | rejections counted, one audit entry per peer per hour |
| Frame leaks into chat or another bearer | classified before rules and persistence, never forwarded, never broadcast |
| Egress rules bypassed for replies | bounded by the per-peer budget and the paid-bearer minimum interval; documented in the UI |

## 14. Field status (2026-09-02)

Deployed to both field kits on 2026-09-02 (pipeline 51576; parallax received the image through a chunked, resumable transfer because its WiFi windows were shorter than a registry pull). Proven on real hardware and carriers: cross-kit pairing (tesseract issues the key in a signed QR bundle, parallax imports it and auto-registers the peer, same peer id on both sides); the SMS request leg tesseract to parallax, encrypted and clear, decoded, authenticated, replay-checked and executed with the reply sealed and queued within four seconds; the Hub route (`POST /api/bridges/{id}/command` with `mgmt_ping` on both kits and `mgmt_reset` cellular level 1 on parallax) through the shared executor with audit entries and metrics.

Not yet observed, each for a reason outside this protocol: the reply leg parallax to tesseract over SMS (the carrier delivered no SMS from parallax's SIM to tesseract's; suspected prepaid balance); APRS in either direction (both kits transmit and receive nothing, the radio receive path needs hands on the kits); the mesh bearer on parallax (radio wedged, power cycle needed). A lesson recorded the same night: never send AT+CUSD through the bridge on the A7670E, the pending USSD session blocked the modem's AT channel until a power toggle.
